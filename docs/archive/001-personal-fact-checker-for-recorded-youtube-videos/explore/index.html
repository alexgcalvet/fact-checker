Three questions explain this repo.

Pick your depth

What this is

A second, critical ear for a YouTube interview: short flags on the player that quote what was said, say what is wrong with it, and cite the source.

The problem

In a political interview, figures, contradictions and dodged questions go by too fast to check. A viewer either trusts the speaker or pauses to search, and loses the thread.

The solution

A helper on the viewer's own machine reads the captions part by part with a language model, checks each central figure against published sources, and writes flags. The extension shows each flag on the player at its second, with a confidence.

Who it is for

Viewers of Spanish and English interviews and debates, beta testers who mark flags as fair or unfair, and the owner who reviews the analyses they share.

How it works

  1. WatchThe extension reads the video and the playback second, and asks the helper to analyse.
  2. TranscribeThe helper fetches the captions with yt-dlp, or transcribes the audio with Whisper, and separates the voices.
  3. Read and checkThe pipeline reads each part, checks the central claims, and a judge reviews every flag at the end.
  4. ShowFlags appear on the player at their second; the rest wait in the side panel.
  5. ShareWith consent, marks and whole analyses go to the owner's collector.

What happens

Step 1 is in progress in docs/RFC.md. Steps 2 and 3 start only after Step 1 meets its precision target.

Why

Recorded videos first: no latency pressure, cheaper, and testable on a golden dataset.

A viewer watches a YouTube video and sees, at the exact second, short flags on what is said. Step 1 runs on each person's own machine with their own subscription or API key. Step 2 moves the pipeline to a server so that every video is analysed once for every viewer, and adds a web page and a shareable report. Step 3 brings live streams.

Seams to keep open

  • The pipeline is a stream of chunks with no I/O. Step 2 runs it on a server unchanged; Step 3 feeds it a live transcript.
  • The LLM provider is a port. A new provider is one adapter file plus a provider value.
  • The extension reads flags from one HTTP address. Step 2 changes only the address.
  • The flag file is a public contract. The collector, the web page and the report page read the same format.

Intended decisions

  • Flags over the player only in the extension. YouTube API policies forbid covering an embedded player, so the web page shows them beside it.
  • Each person pays their own readings in Step 1. The owner pays only the collector, on the free plan.
  • Step 2 budget: at most €3 per video-hour (docs/research/interview-youtube-fact-checker.md), so a free tier stays viable.

What you see

Each card quotes the words, names the type, gives a reason, a confidence and, for a figure, its source. You can mark it as correct or unfair.

What happens

A content script on youtube.com talks to a service worker, and only the service worker calls the helper on 127.0.0.1.

Why

Chrome blocks a content script from calling localhost, and a viewer needs no account: the helper does all the work.

The extension is only the display. It reads the video id and the playback second on youtube.com, polls the helper, and draws what the flag file says. It holds no logic about what is true: it decides only where and when a flag shows.

How it works

  1. Load on youtube.com

    A Manifest V3 content script runs on each watch page, reads the video id and the player's current second, and draws in the page. A background service worker does every fetch to the helper, because only it may call 127.0.0.1.

    src/extension/manifest.json · src/extension/src/content.ts · sw.ts

  2. Find the helper

    The service worker asks /health on ports 8765 to 8769 and keeps the first one that answers as fact-checker. If none answers, the extension says that the helper is down, with the fix.

    src/extension/src/sw.ts

  3. Poll and draw

    Each poll sends the playback second and gets the flag file so far. A flag with on_player: true shows as a card on the player for 8 seconds, unless the viewer pins it. Every flag appears in the side panel and as a mark on the strip under the video, so a click jumps to its second.

    src/extension/src/overlay.ts · panel.ts · flags.ts

  4. Mark and set

    A vote on a card says whether the flag is correct or unfair, with a reason. The ⚙ menu holds the language (Spanish or English, from the browser by default), sharing, and quiet mode, which shows only serious flags. The settings live in chrome.storage; the sharing answer goes to the helper.

    src/extension/src/panel.ts · texts.ts · _locales/

  5. Export a card

    For a finished video, a button opens the helper's summary page: the profile card of each guest as an image, with its alt text ready to copy.

    src/extension/src/panel.ts

Why this way

  • The built extension ships inside the helper package. A person needs no Node.js: setup copies it to ~/.fact-checker/extension. Beat: a committed dist/.
  • Interface language from the browser. es* gives Spanish, anything else English, with a choice in ⚙. Beat: chrome.i18n, which cannot be switched in tests.
  • A bar per flag type, the side panel lists everything. Precision on the player, nothing lost. Beat: a user slider.

Limits

  • Loaded unpacked. It is not in the Chrome Web Store; the person loads the folder by hand.
  • youtube.com only. Embedded players on other sites are not covered.

What happens

A small HTTP server on localhost starts analyses, follows the playback second, and keeps every result in the helper home.

Why

The model readings run on the person's own subscription, so neither the person nor the owner pays per video.

The helper is a Python package with two entry points: serve, the HTTP API that the extension calls, and the CLI for a person or an agent. Install puts it on the machine and starts it at login. Both entry points hand the work to the pipeline and keep the result in one flag file per video.

How it works

  1. Install in one step

    install.sh installs uv, yt-dlp, ffmpeg (from the imageio-ffmpeg wheel) and the helper, each only if missing, then runs setup. A person can also tell their AI agent to follow INSTALL-AGENT.md, and the agent names its own provider.

    install.sh · INSTALL-AGENT.md

  2. Set up and check

    setup checks claude or codex (logged in), uv, yt-dlp, ffmpeg and Chrome. It writes config.toml with the logged-in agent CLI, copies the extension, and starts the helper at login: a launchd agent on macOS, a systemd user service on Linux. doctor prints one line per check with its fix, and key set stores a key from a hidden prompt.

    src/helper/fact_checker/install.py

  3. Serve on localhost

    serve takes the first free port of 8765–8769 and answers /health, so the extension and doctor can tell it from another program. It picks the provider and model of each role from config.toml, runs one analysis per video in a thread, and follows the playback second of each poll.

    src/helper/fact_checker/server.py

  4. Run by hand

    The CLI runs the same work without the extension: analyze <url> reads a whole video, judge <id> reruns the judge, eval scores the golden dataset, and feedback and shared talk to the collector.

    src/helper/fact_checker/cli.py

  5. Keep the result

    Each video has one flag file in ~/.fact-checker/videos/. The helper writes it after each part, so a poll always gets the flags so far, and a finished file is served again with no new reading.

    src/helper/fact_checker/store.py

Why this way

  • A local helper on the person's own subscription. Claude Code by default, else Codex; an API key is an option. Beat: a paid backend.
  • Python helper, TypeScript extension. yt-dlp, Whisper and pyannote are Python. Beat: all TypeScript.
  • Hard stop at 60 readings per started video-hour. A failure cannot exhaust the subscription. Beat: no limit.

Limits

  • macOS and Linux only. Windows comes later.
  • All five ports taken: the helper logs one line and exits; the login agent does not loop.
  • Started inside an agent's sandbox, the helper cannot write its home; /health says writable: false and doctor names it.

What you seeNothing directly: the pipeline is what decides each card. Its choices show as the type, the reason, the confidence and the source of a flag.How it works and why

What you see

Six flag types: fallacy, bias, contradiction, inaccuracy, question and context.

What happens

Up to five model readings per part: screen, part, search, verdict, and the judge once at the end.

Why

False positives cost more than misses, so each step leans to precision.

The pipeline turns a stream of caption parts into flags. It has no I/O: it reaches the captions, the models and the searches only through ports. Each part is read with what was said before it, so a recorded video and a future live stream use the same code.

How it works

  1. Plan the parts

    The scheduler orders the parts from the playback second forward, then the earlier ones. It keeps a budget per role of 60 readings per started video-hour, and starts no part more than 10 minutes after the last second heard.

    core/scheduler.py

  2. Screen

    A cheap model reads the part alone and answers whether it may hold anything worth a full reading. Only an explicit read: false skips it: small talk, greetings, adverts. An error or any other answer reads the part.

    core/pipeline.py (screen)

  3. Read the part

    One reading returns the fallacies from a closed list of 11 labels, the checkable claims, the questions with how they were answered, the contradictions with an earlier statement, at most 2 context cards, and the new positions of each speaker. The quote of each item is matched to the caption words to find its exact second and voice.

    core/pipeline.py (analyze_chunk)

    Without contextA part alone cannot see that the speaker said the opposite 20 minutes ago.

    With itIn conversation mode, one model session reads the parts in order; a positions list of up to 60 lines carries what each speaker stated earlier in the video.

  4. Check the claims

    Only claims marked central and not repeating an earlier one go on. Published fact-checks come first; then a search reading gathers evidence and a verdict reading, with no tools, judges it. The code, not the model, decides the label: one credible measure for the figure and one against make it disputed; false needs every credible measure against it and one from tier 1–3.

    core/factcheck.py · adapters/factcheck_google.py

  5. Judge the whole

    When every part is done, one reading per started two video-hours sees the whole transcript with speakers and rules on each flag: keep, or nitpick for a small slip. It rates each kept flag minor, moderate or serious by materiality, centrality and magnitude, never intent, and can correct the speaker.

    core/judge.py

Why this way

  • A cheaper model searches, a strong one judges; central claims only, once per video. About 70 % of a video's cost was strong-model fact-checks resending every search result. Beat: one model for both, every figure checked.
  • An official figure is not the truth by itself. Sources weigh by a tier of independence, so the checker does not take a side. Beat: official data as ground truth.
  • A closed list of fallacy labels. Each is visible in the words and has few false positives; any other goes to candidates.log, never the screen. Beat: an open list.
  • The judge never drops a flag. Rule keep or nitpick only, so it stays reversible. Beat: rewriting or deleting flags.

Limits

  • Repeats in flight. With 3 parts at once, a claim repeated in a part still being read is checked twice.
  • The screen can hide a flag. A part it skips is never read; that is why it leans to reading.
  • Claims are judged on the publish date. A newer value goes into note, not the verdict.

What happens

Why

A new provider or source is one new file, with no edit elsewhere.

Adapters connect the pipeline to the outside world: the words of the video, the voices, the language models and the sources. Each adapter implements one port, so the pipeline never knows whether a reading ran on a Claude subscription, ChatGPT or an API key.

How it works

  1. Words and date

    yt-dlp fetches the automatic captions as json3, preferring the original-language track (es-orig, en-orig) so a translated track never wins, plus the title, channel, duration and publish date. With no usable captions, the audio is transcribed by Whisper in a separate uv run --script, so the helper has no heavy dependency.

    adapters/youtube.py · whisper.py · whisper_cli.py · faster_whisper_cli.py

  2. Voices

    With HF_TOKEN, pyannote separates the voices of the audio on the laptop, and each caption word gets the voice heard at its second. Without it, the part reading guesses the speakers from the text.

    adapters/diarization.py · diarize_cli.py · core/speakers.py

  3. Readings

    Every reading is complete(prompt, schema, tools) and returns JSON that matches the schema. The fixed rules go in the system prompt, the same text each time, so the provider reads them from cache. Each reading is logged with its tokens and cost to usage.log; a model with no known price logs a null cost.

    adapters/llm_claude_cli.py · llm_codex_cli.py · llm_anthropic_api.py · llm_openai_api.py · llm_chat_api.py · core/prices.py

What happens

fact-checker eval runs the pipeline on synthetic dialogues with planted errors and sets a confidence bar per flag type.

Why

A noisy feed gets ignored. Precision first.

Quality is measured, not guessed. A golden dataset of synthetic Spanish dialogues with planted errors gives each flag type a bar: the lowest confidence at which the type is right at least 80 % of the time. The viewer's marks are the second signal.

How it works

  1. Synthetic dialogues

    One JSON file per topic, such as empleo.json or pensiones.json, each a dialogue with planted errors and the flags it should produce. They are invented, so no real conversation is committed.

    tests/golden/

  2. Score

    fact-checker eval runs the pipeline on each dialogue and matches found flags to expected ones, by type, for precision and recall.

    src/helper/fact_checker/cli.py · core/score.py

  3. Set the bars

    eval --save writes, per type, the lowest confidence with precision of at least 0.80, or null (never on the player) with fewer than 5 flags. Another provider gets its own file, thresholds.<provider>.json.

    src/helper/fact_checker/thresholds.json

  4. Learn from marks

    Each correct or unfair mark goes to marks.jsonl. judge --against-marks and eval --marks compare the pipeline and the judge with them, so a change can be measured on real disagreements.

    ~/.fact-checker/marks.jsonl

Why this way

  • A bar per flag type from measured precision, per provider. Precision on the player, nothing lost. Beat: fixed levels at 0.80 and 0.50.
  • Every speaker is analysed alike. A flag is about what is said, not who says it. Beat: only the interviewee.

Limits

  • The dataset is Spanish only. English videos use the same bars.
  • A real eval spends model readings on the person's subscription or key.

What you see

What happens

The helper sends each mark and each finished analysis to the owner's collector; the owner approves an analysis before anyone else gets it.

Why

The cost of a video is paid once, not per viewer, and nobody can plant flags.

Sharing turns a personal tool into a common one. With consent, marks teach the owner where the pipeline goes wrong, and an approved analysis is served free to the next viewer of the same video and language. The summary turns a finished, reviewed video into a profile card per guest.

How it works

  1. Send each mark

    After the person says yes once, each mark sends itself in the background, in batches of up to 50. A mark given with sharing off is kept with shared: false and never leaves. The owner reads all marks with feedback pull.

    src/helper/fact_checker/feedback.py

  2. Upload a whole analysis

    When an analysis is done, the helper uploads it stripped to the shared fields: no file paths, no install id inside. It waits as pending until the owner approves it, unless the owner uploads it with the admin token.

    src/helper/fact_checker/analyses.py

  3. Keep and guard

    The collector, a Cloudflare Worker with a D1 database, keeps marks and analyses with hard stops per install id: 20 mark requests and 10 uploads per UTC day. A served analysis is replaced only by one from a higher-ranked parts model.

    src/collector/src/index.ts · schema.sql

  4. Approve

    The owner lists pending uploads with fact-checker shared list, and approves or rejects each. An approved analysis is also a public read-only page at /a/<video_id> with each flag, its severity, its sources and the rubric.

    src/helper/fact_checker/cli.py · src/collector/src/index.ts

  5. Make the card

    For each guest, the summary counts only the flags marked correct, fills an HTML card in the CALVET brand with bundled fonts, and headless Chrome turns it into a 1080×1350 PNG with alt text of at most 1,000 characters. A comparison card puts up to three people side by side, once every flag of each is marked.

    core/summary.py · summary.html · adapters/screenshot.py · adapters/thumbnail.py

Why this way

  • Consent first, then automatic. Testers missed a send button. Beat: a send button; asking at install.
  • A shared analysis is whole and approved. Nobody can plant flags; the best reading wins. Beat: serving every upload.
  • Cloudflare Workers + D1. Free plan, one deploy, and a D1 row holds a whole flag file. Beat: a hosted form or sheet.
  • Only guests on a card; rates per hour of speech, no score. A partial review would compare the reviewer's effort. Beat: a single score per person.

Limits

  • The owner reviews every upload by hand. That is the first limit on growth.
  • The card needs marks. Without flags marked correct, a guest's card is empty.

fact-checker key set asks for a key without echoing it; ⚙ shows whether sharing is on.

What happens

The helper listens only on 127.0.0.1, keeps quotes and keys in the helper home, and sends only what the person allowed.

Why

Conversations are personal data, and keys spend the person's money.

Two things need protecting: the person's keys and logins, and the quotes of real videos. Both stay in the helper home on the person's machine. Only marks and analyses leave, only after consent, and only to the owner's collector, which keeps no name, email, IP or path.

The rules in force

  • Localhost only. The helper listens on 127.0.0.1. Only the extension's service worker calls it, never a content script.
  • Keys from a hidden prompt. fact-checker key set writes .env with mode 600; doctor names a missing key, never its value. The Google key is restricted to the Fact Check Tools API.
  • Consent before anything leaves. Nothing goes to the collector before share_marks is true; a mark given with sharing off never leaves.
  • Nobody can plant flags. A stranger's upload stays pending until the owner approves it.
  • No real conversations in the repo. Tests use synthetic dialogues and recorded, sanitized responses in tests/fakes/.

Limits

  • The helper cannot identify the extension. A GET from the service worker carries no Origin, so any local program can call the helper.
  • Quotes leave with a shared mark. A mark carries the quote (up to 1,000 characters) of a public video.

Security and privacy

What stays on the machine, what leaves after consent, and who holds each key. PRIVACY.md and SECURITY.md hold the public texts.

Flag
One finding on the player: it quotes the words, names a type (fallacy, bias, contradiction, inaccuracy, question or context), gives a reason, a confidence and, for a fact, a source.
Confidence
A number from 0 to 1 that the model gives each flag. It decides whether the flag reaches the player.
Bar
The lowest confidence at which a flag type shows on the player, set per provider from the golden dataset.
Part (chunk)
A stretch of the captions read in one reading: 30 seconds first, then 2 minutes.
Role
A job of the models: parts, screen, search, verdict or judge. Each role can have its own provider and model.
Provider
Who runs a reading: claude (Claude Code), codex (Codex CLI), anthropic, openai or chat.
Screen
A cheap reading before the full one that skips a part of pure small talk.
Judge
One reading of the whole transcript after every part, which rules keep or nitpick on each flag and rates its severity.
Nitpick (puntualización)
The judge's verdict for a small slip whose substance holds. The flag stays, marked as minor correction.
Severity
Minor, moderate or serious, by materiality, centrality and magnitude; never by intent.
Positions list
What each speaker stated earlier in the video, one line each, sent with each part so a contradiction can be found across the video.
Conversation mode
One model session reads the parts in order, each as the next message. Window mode instead sends the 3 minutes before each part.
Port
An interface of the pipeline, such as LLM or Transcript. An adapter implements it for one external system.
Golden dataset
Synthetic Spanish dialogues with planted errors and the flags they should produce, in tests/golden/.
Helper home
~/.fact-checker/: flag files, logs, marks, settings and keys of one machine.
Collector
The owner's Cloudflare Worker with a D1 database that keeps shared marks and analyses.
Install id
A random UUID per machine, used by the collector's daily limits; it names no person.
Diarization
Separating the voices of an audio track, done here by pyannote.
ClaimReview
The format of published fact-checks that the Google Fact Check Tools API returns.
Tier
The independence of a figure's producer, from 1 (independent statistics) to 5 (think tanks and media).
MV3
Manifest V3, the current format of Chrome extensions: content scripts plus a service worker.
D1
Cloudflare's SQLite database for Workers.
